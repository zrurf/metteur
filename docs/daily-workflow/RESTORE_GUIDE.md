# 升级、冷备份与回退

2026-10-23。保护承诺以宿主ACK为界；未确认的本窗口输入先导出或等待备份。页面、工作区、daemon和整机是不同边界，见LIFECYCLE.md。没有持久浏览器正文缓存；业务rewind不清理输入恢复namespace，整库回退则需要额外保全新输入。

当前版本可读取R8的会话、运行和文件，在既有数据库CF中增加独立恢复/投递/控制namespace，不重置旧记录。未知schema、损坏和容量不足会明确拒绝保护，不截断正文或静默删除唯一副本。当前模型/资源权限在使用时重新校验；恢复输入不会恢复full、AllowOnce或已撤销策略。

2026-10-23复核修正另增加恢复namespace marker2：首次回收已保存/丢弃的旧标记时才原子升级并写入creation_epoch，活动稿正文不删除。上一交付宿主ccecd9c只识别恢复marker1，因此升级后的恢复库也不能直接交给该旧宿主；回退同样遵守下面的冷副本与新增稿导出流程。遗留4096条记录的回收、WAL失败原子性、活动稿保留和重新打开后的旧请求拒绝已在REVIEW_FIXES.md记录；不将这些定向检查冒充重复的全套R8演练。

**R8不能原地复用写入新namespace后的数据库。** 实测R8仍能读文件及会话，但ListExecutions把新存储项当旧checkpoint，返回缺run_id的错误；它也没有Recovery RPC。原失败和当前恢复副本未变的核对在`s4-r8-current-roundtrip`。这不是可承诺的旧版保护能力。

安全路径：

1. 升级前关闭工作区及其运行，保存项目整目录冷副本，连同`.metteur`；用户/个人资源数据目录另外保全。不能把热RocksDB文件复制称为一致备份。
2. 当前版先等待所需草稿的Backed Up on Host，再从Recovery Copies预览/导出未解决输入。保留当前完整冷副本以及原始文件，不用旧副本覆盖唯一新稿。
3. 回退R8使用升级前冷副本，在原路径打开。当前版目录先另存保留，新的草稿导出单独保存；R8中需要的文本由用户明确复制，不能宣称其已被新版恢复系统保护。
4. 回到当前版时，先保留R8期间的新改动，再把当前版冷副本恢复到其原路径。恢复列表按原workspace/owner身份读取，不能简单移动数据库后承诺所有引用仍有效。双方文件按差异比较后明确保存，不自动覆盖回退期间的新文件。

`s4-r8-cold-upgrade-rollback`已用保留且摘要匹配的真实R8和当前Windows程序执行全流程：R8会话/文件/真实run升级可读；新草稿ACK后单独导出；R8用升级前冷副本能正常列原run；返回当前版时ACK原稿及R8期间的后续编辑分别保留。没有删除历史目录、执行付费模型或读取用户项目。

`s4-cold-restore-fixture-fix`另验证当前版同路径冷恢复：整个副本逐文件SHA256一致，四类草稿、原会话/蓝图及BOM/CRLF文件保持，恢复前后续改动保留在另一个目录。首次演练夹具误从不存在的ExecutionEvent.runId取ID，改用实际ListExecutions身份后通过，原失败保留。演练副本/哈希/导出均在证据目录，不能拿合成副本替换用户真实项目。

候选程序及源码摘要见运行manifest；旧冻结程序、原失败证据及副本不删除。Linux本阶段验证真实DB/文件/RPC及来源生命周期；上述实际R8二进制回退演练在Windows执行，不冒称Linux桌面验收。
