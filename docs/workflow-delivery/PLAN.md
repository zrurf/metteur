## 2. 交互流程

1. 从聊天计划或蓝图编辑入口选择 `Start from template`。显示四类用途、输入要求和阶段；选择不保存、不调用模型、不执行命令。
2. 填写名称、目标、修改范围、需要保持不变的约束、基线检查及最终检查命令、证据文件、模型与有限迭代设置。模板不捆绑模型/外部服务；已选 Prompt 仍需原资源选择。文件范围是任务约束，不能扩大 sandbox 权限，也不能假装已经强制限制所有 shell 副作用。
3. 编辑逐项要求：稳定 ID、说明、必需/可选、确定性检查或人工审阅。展示检查命令、预期退出码、将运行的次数与权限类别；空命令/缺依赖不能被默认为通过。
4. `Preview plan` 调用宿主目录/编译器，只生成普通蓝图及校验信息。默认阶段清单，展开可查看节点。`Create blueprint` 使用既有 create-only 文件写入、版本/mirror 流程；同名不覆盖；取消保留当前表单草稿。
5. 已创建实例由普通编辑器编辑/恢复/保存。模板版本仅作来源，升级模板不修改已有实例。进入底层编辑后表单不能静默重建覆盖；再次应用模板要新建实例或明确审阅差异。导入/导出不能丢验收契约；不支持的格式明确提示。
6. 发起执行沿用原启动路径；聊天发起仍冻结源会话与完成策略，编辑器直接运行仍是独立运行。运行前显示要求与精确版本；改变要求、命令、Prompt 或依赖使旧确认失效。选择模板不等于批准 Run。
7. 执行时展示阶段与检查，不额外启动一个规划/任务执行器。主聊天保留历史/草稿，监督从独立入口进入。停止、审批、预算/未知效果仍由原宿主控制。
8. 结果页按要求显示 `Passed / Failed / Missing / Skipped / Stale / Needs review`，打开真实命令输出、文件/版本与运行来源。执行终态、确定性检查和人工验收分别呈现。
9. 用户可记录逐项 `Accept / Request changes` 及说明。接受绑定当前运行、要求、证据版本与认证主体；它不批准命令、不修改任务预算、不自动继续。修改要求/产物后保留历史接受，当前状态转为需复验。
10. 失败后使用已有 `Add result to draft / Prepare new proposal`；带上未满足要求和来源，由用户明确发送。无隐藏重跑、无复制任务清零预算、无原会话被完成事件抢走。

## 3. 四类模板与验证含义

| 模板 | 阶段 | 最低独立验收 |
|---|---|---|
| Fix a bug | 重现并确认预期失败 → 局部修复 → 回归与约束检查 → 审阅 | 固定用例修改前失败、修改后通过；无范围外意外改动 |
| Add tests | 确认当前行为 → 增加测试 → 执行测试及指定缺陷检出检查 → 审阅 | 新测试验证冻结行为，并能捕获指定缺陷；生产行为保持 |
| Refactor safely | 记录行为基线 → 重构 → 固定行为/接口对照 → 审阅 | 固定输入输出、公开接口及既有测试保持；不能只用新写测试自证 |
| Add a small feature | 明确正常/边界/失败要求 → 实现 → 独立验收及回归 → 审阅 | 三类场景与相关回归通过；未请求的行为变更明确显示 |

默认阶段级 ReAct 节点，复用 CallLLM、命令、JsonGet、Validator 等现有目录；不新增规划引擎。阶段可编辑，节点细节按需展开。检查节点必须来自运行目录，不伪造结果文本。修 bug 的基线失败须匹配明确预期退出码，超时/工具失败/未知不可视为成功重现。最终检查通过也不等于用户接受。

## 4. 数据、版本与可靠性契约

- 唯一权威仍是蓝图文件。模板实例 UUID 与模板 ID/revision 分离，实例命名不能决定身份；同一逻辑创建请求重试不产生另一实例。验收契约以带 schema 的节点元数据保存在图内，经现有版本、恢复、精确确认一起冻结，不创建第二份可变计划。
- 模板编译严格校验四类 ID、字段/大小、检查数量、唯一要求 ID、有效节点引用、路径与必需输入。普通图仍保持“必填引脚未连是警告”的既有规则；模板字段规则不改成全局图禁令。
- 检查记录取宿主真实 invocation/current attempt/check，不接收前端或模型提交的 passed。只有匹配冻结契约的对应检查才能满足要求；跳过/缺记录/未知/不匹配版本不能通过。
- 运行时保存要求和证据绑定，查询不读取最新可变蓝图冒充旧版本。证据文件路径限工作区普通文件，拒绝元数据、越界、符号链接逃逸；明确大小/数量上限。每条证据标明覆盖范围；shell/网络等未追踪效果如实说明。
- 检查后的文件变化、后续写入、蓝图契约变化和证据不可读产生 stale/unavailable。采用确定性内容摘要与检查版本关联；不能只比较文件名或模型文字。未知证据不自动重测。
- 人工记录走专用用户控制 RPC，模型和插件没有入口。认证主体/工作区/run 由宿主核验；具体内容摘要、expected revision 和请求 UUID 共同绑定。重复请求返回同一回执，同 ID 不同内容拒绝；多窗口冲突保留输入。
- 审阅是低频、追加历史且不参与执行 rewind 的资源；设每 run 要求/修订/总字节上限，达到上限明确拒绝，不静默删除历史或活跃草稿。读回失败不能显示“已接受”。断连未知保留请求身份，对账后才能提交新决定。
- 老图无契约时保持旧结果展示，明确 `No acceptance criteria`，不推断旧图通过。新契约未知 schema 拒绝受保护流程并保留原始文件；兼容升级使用冷备份及原数据对照。历史人工 IME/S3 接受边界不被改写。

## 5. 预检、预览与故障

预检只读：字段、当前节点目录、配置的模型、文件/依赖可用性与已知权限；不执行用户检查命令/安装依赖/探测付费端点。静态无法证明的工具可用性显示待执行验证，不谎称环境通过。

预览分 WD-PV-01 模板/计划/启动确认、WD-PV-02 结果/逐项审阅/失败继续。沿用 SPEC §8.1.12：在隔离目录实现并标 fixture，指定 preview_id/revision 供用户确认后才接生产路由。后端、测试、对照样本可独立推进。13–14px 正文/主要操作、18px 标题；默认信息有限，预算/内部 ID/长诊断收起。键盘、焦点、取消、窄屏、浅/深色均覆盖。

必须覆盖编译失败、保存/mirror 失败、确认后变化、执行被占用、检查超时/非零、停止、预算耗尽、未知副作用、文件缺失/修改、旧证据、跨工作区/用户、重复/迟到请求、刷新/重启及表单未保存恢复。任何失败不得清草稿、误报接受或隐式发起模型调用。

## 6. 三模式对照

固定四个完整仓库任务（四类各一），每个在相同初态、同一模型/工具/权限/总预算规则下运行 ReAct、P&E、P&E+监督，共 12 单元。任务、独立判据、顺序和失败处理在首个模型请求前冻结；开发夹具与评测样本分开。监督只在第三模式启用，其他差异公开。蓝图规划与用户准备时间均记录，不能把人工制作模板的成本隐藏成零。

独立评判检查真实文件、命令/测试结果和范围外改动；模型生成的测试不单独作为金标准。记录完成/失败/未完成、人工介入、重试/恢复、墙钟时间、生成请求、输入/输出/cache/reasoning 用量及缺失覆盖。规划、执行、验证重试、客服/监督全部计入同一试验账本；未知用量不填零。冷/热缓存条件记录，不保证厂商命中。

用户于 2026-10-24 授权本阶段真实模型评测在 US$3 内自由调用。真实调用使用新独立账本，规划、执行、监督、重试全部累计，设置 US$3 总费用及有限请求硬上限，不复用历史 US$1/US$5。运行器及离线检查通过、具体样本/模型/上限冻结后即可在该授权内执行，无需再次询问同一预算；尚未执行时仍标 NOT_RUN。失败样本保留，修复后只定向复验并标明原因，不择优抹去首轮。小样本只指导模式选择，不设预定省钱百分比。

## 7. 交付与验收

完整 AC 与状态见 TASKS。先集中完成相同场景的实现、反例及夹具后检查；修复只复测失败/受影响项。证据分类型/宿主/隔离预览/生产链/真实模型/平台，不能互相冒充。既有未受影响证据复用，不无理由重跑历史全矩阵。

交付必须包括四类可用模板、逐项记录和版本失效、12 单元真实对照报告、用户确认的界面、旧数据兼容、使用/恢复说明及清晰的任务状态。四类各有完整任务成功交付证据；三模式的模型失败如实记录，产品缺陷修复后验收。费用或预览尚未授权时相应项明确未完成，不能宣布阶段收口。
